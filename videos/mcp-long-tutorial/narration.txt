模型看见订单号，为什么还查不到物流？因为它像一个会分析问题的人，却没有进入订单系统的门卡。MCP 就是这套通用门卡规则。今天只跟着一张订单便签走一遍，看它怎样找到工具、进入系统，再带着真实结果回来。

模型可以用 Function Calling 写出一张调用单，说明它想查哪个订单。但写出调用单，不等于真的有人接单。MCP 补上的是后半程。Client 像接线员，负责寻找能力；Server 像办事窗口，负责真正执行；中间的传输通道负责把消息送到。模型决定做什么，MCP 负责把这件事接到真实系统。

Client 找到 Server 后，先不能办业务，要像两个人通话前先确认彼此听得懂。Client 先发起初始化，Server 回答自己支持的版本和能力，Client 再确认收到。完成这三步，连接才进入就绪状态。这样版本不兼容或连接超时，会在业务调用之前被发现。

连接就绪后，Client 会问 Server，你现在能做什么？Server 返回工具清单和每个工具的参数规则。比如查询订单需要一个不能为空的订单号。模型从用户的话里取出订单号，按规则填好。少填或填错，会在进入订单系统前被拦住。这就是动态发现，模型不用提前把所有工具写死。

现在调用单进入 Server。第一关检查参数，第二步查询订单系统，第三步返回结果。结果既可以有给人看的文字，也可以保留订单状态、快递公司和单号这些结构化字段。模型最后把结果说成人话。关键分工是，模型选择工具并解释结果，Server 才真正接触企业数据。

MCP 里常见三类能力。Resource 像资料柜，用来读取订单状态说明。Prompt 像办事模板，告诉模型怎样组织任务。Tool 像操作按钮，真的执行查询或修改。可以先读资料，再套用模板，最后按下工具。一个给内容，一个组织任务，一个执行动作。

消息怎么传过去？本地工具常走标准输入输出。Client 启动一个 Server 进程，每条 JSON RPC 消息各占一行，写入标准输入，再从标准输出读回结果。日志要走另一条通道，不能混进协议。远程服务常走 HTTP，会话编号像通行证一样跟着请求。断线可以续接；会话过期收到 404，就重新初始化。

一个 Agent 往往会连接订单、知识库和备用服务。两个 Server 可能都提供同名工具，所以工具名要带上来源，例如订单服务斜杠查询订单，备用服务斜杠查询订单。Gateway 像总接线台，汇总能力并把请求送到正确线路。某个 Server 离线，只关闭自己的线路，其他服务继续工作。

查询只是读取，取消订单却会改变真实业务，所以要多几道闸门。密钥只留在 Server，模型拿不到。高风险请求先暂停，生成人工审批单，批准后才执行。系统还会限制调用频率和访问范围。最后写审计记录时，令牌等敏感内容会被遮住。

取消任务也不能只把页面上的按钮藏起来。取消信号要从管理接口传到正在运行的任务，再传给 Client 和 Server。底层真正停下后，状态才变成已取消。已经完成的付款或删除不会自动倒退，这类操作还需要业务补偿机制。

协议跑通只是第一步，系统还要能管理。数据库保存 Server 配置和能力清单，每次调用都有一张记录，写清状态、耗时、结果和错误。高风险请求进入审批中心，事件时间线则还原一次调用从开始到结束发生了什么。这样出问题时，才能查清哪一步失败。

这个项目手写主链，是为了把连接、发现和调用拆开给你看，不是要替代成熟框架。FastMCP 已经提供认证、中间件和任务等工程能力。项目再用 Inspector 检查握手、工具、资源和模板是否能正常工作，并明确标出还没有覆盖的功能边界。

回到开场，模型不是突然学会了公司的数据库。它只是通过统一规则完成四件事。先连接 Server，再发现能力，然后按规则调用，最后接受审批、取消和审计。Function Calling 让模型说出自己想做什么；MCP 让外部系统说明自己能做什么，以及怎样安全地做。完整源码、流程图和兼容报告都在 lobster bujiaban 的 lob mcp。

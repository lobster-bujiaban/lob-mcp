# 《MCP 到底解决了什么？一条订单请求看懂 Client、Server 与工具网关》视频设计

## 一、视频定位

- 系列：LOB AI 源码研究长视频
- 项目：LOB MCP
- 参考源码：FastMCP 4.0.1、MCP 2025-06-18
- 目标受众：会调用大模型 API，但尚未系统理解 MCP 的 AI 应用工程师
- 核心承诺：不背协议名词，用同一个订单请求跑完“连接、发现、调用、治理、观测”完整链路
- 建议时长：8～10 分钟
- 画幅：1080×1920，9:16，30 FPS
- 旁白：`zh-CN-XiaoyiNeural`，建议语速 `+20%～+24%`
- 仓库：`lobster-bujiaban/lob-mcp`

## 二、核心叙事

全片只追踪一个红色订单请求便签：

```text
“查一下 ORD-20250902-001 到哪了”
```

这张便签从用户手中进入 Agent，经 MCP Client 完成握手和工具发现，穿过 stdio 或 HTTP，到达订单 Server，再带着结构化结果返回。后半程将同一订单改成“取消订单”，触发审批、凭据、限流和审计。

全片回答五个问题：

1. Function Calling 已经能调函数，为什么还需要 MCP？
2. Agent 如何连接一个此前不认识的 Server？
3. Tools、Resources、Prompts 到底有什么区别？
4. stdio、Streamable HTTP 和多 Server 如何工作？
5. 企业系统接入后，凭据、审批、取消和审计应该放在哪里？

## 四、章节与分镜

### 01｜开场：模型知道订单号，却查不到订单（0:00～0:35）

旁白任务：用真实失败制造观看理由。普通模型只能回答“请联系商家”，因为它没有企业系统入口。

手绘画面节拍：

1. 用户递出订单便签：“ORD-20250902-001 到哪了？”
2. 模型脑袋旁出现训练数据书架，却没有订单数据库。
3. 数据库在一堵墙后面，模型伸手够不到。
4. 完整链路缩略图闪现：Client → Server → 订单系统 → 结果。

关键字幕：

- “模型会推理，不等于能访问企业系统”
- “MCP 管的是能力连接，不是替模型思考”

源码证据：`README.md` 第 19～44 行。

### 02｜先分清：Function Calling 与 MCP（0:35～1:15）

旁白任务：解释 Function Calling 是模型输出结构化调用意图；MCP 解决的是能力如何被发现、连接和执行。

手绘画面节拍：

1. 左边画模型吐出一张纸：`order.query {order_id}`。
2. 纸张停在半空，旁边批注：“谁来执行？”
3. 右边补上 MCP Client、Transport 和 Server。
4. 用括号圈出：Function Calling 位于“模型决策”，MCP 位于“外部能力层”。

画面关系：前后补全，不使用简单左右产品对比卡。

### 03｜第一次握手：不是连上就能调用（1:15～2:00）

旁白任务：讲清 `initialize → response → notifications/initialized → ready`。

手绘画面节拍：

1. Client 把 initialize 信封放进紫色管道。
2. Server 回寄协议版本、ServerInfo 和 capabilities。
3. Client 盖章 `notifications/initialized`。
4. Client 状态从 disconnected 逐格变成 ready。

视觉重点：做成“握手协议小剧场”，不要展示大段 JSON。

源码证据：

- `src/lob_mcp/client.py` 第 54～71 行。
- `src/lob_mcp/server.py` 的 initialize 与能力声明。

### 04｜能力发现：模型不是提前写死工具（2:00～2:50）

旁白任务：用 `tools/list` 解释动态发现和 JSON Schema。

手绘画面节拍：

1. Server 打开工具抽屉，取出 `order.query` 卡片。
2. 卡片展开为 Schema：订单号、字符串、必填。
3. Agent 从用户话里圈出订单号，填进 Schema 表格。
4. 漏填订单号时，红笔在执行前打叉，显示 `-32602`。

关键结论：Schema 不是给人看的接口文档，而是模型和 Server 之间可验证的契约。

源码证据：

- `src/lob_mcp/client.py` 第 80～95 行。
- `src/lob_mcp/tools.py`。
- `src/lob_mcp/examples/order.py`。

### 05｜一次工具调用如何闭环（2:50～3:35）

旁白任务：讲 `tools/call`、参数校验、业务执行、content 与 structuredContent。

手绘画面节拍：

1. 订单便签和参数卡一起进入 `tools/call` 漏斗。
2. Pydantic 检查尺量字段。
3. `query_order` 从订单柜中抽出物流卡。
4. 返回两份结果：给旧 Client 的文本、给程序的 structuredContent。
5. Agent 最终写出：“已发货，顺丰，单号……”

源码证据：`README.md` 第 99～105 行，以及 `ToolRegistry.call`。

### 06｜Tools、Resources、Prompts 不是三个同义词（3:35～4:20）

旁白任务：建立三类能力的心智模型。

手绘画面节拍：

1. 三层工具架依次亮起。
2. Tools：一只扳手，表示“执行动作”。
3. Resources：一本订单状态手册，表示“读取内容”。
4. Prompts：一张任务模板，表示“组织消息”。
5. 把三者组合：读状态说明 → 生成任务消息 → 调订单工具。

避免：只放三个定义卡片。必须画出三者如何协作。

源码证据：`README.md` 第 107～113 行。

### 07｜Transport：本地走管道，远程走公路（4:20～5:20）

旁白任务：解释 stdio 与 Streamable HTTP 的适用边界。

手绘画面节拍：

1. 订单便签走左边 stdio 管道：Client 启动子进程，stdin 发送，stdout 返回。
2. stderr 从旁边独立排出日志，红笔注明“不能污染 stdout”。
3. 订单便签转向右边 HTTP 公路：每条消息一个 POST。
4. Session ID 像高速通行证贴在后续请求上。
5. Server 通知从 SSE 回程车道返回；断线后带 Last-Event-ID 续接。

关键字幕：

- “stdio：本地、简单、进程级生命周期”
- “HTTP：远程、多连接、需要认证与会话”

源码证据：

- `src/lob_mcp/transport/stdio.py`。
- `src/lob_mcp/http_server.py`。
- `src/lob_mcp/transport/http.py`。

### 08｜一个 Agent 如何接多个 Server（5:20～6:05）

旁白任务：解释 Registry、并发连接、能力聚合和同名冲突。

手绘画面节拍：

1. 订单、知识、备份三个 Server 插入接线盘。
2. 两张都叫 `order.query` 的卡片碰撞，冒出火花。
3. 接线盘给它们贴上 `orders/` 和 `backup/` 来源前缀。
4. offline Server 变灰，但其他线路继续流动。

关键结论：多 Server 不是把工具数组拼起来，还要处理命名、健康和故障隔离。

源码证据：`src/lob_mcp/gateway.py`。

### 09｜从“查询订单”到“取消订单”，安全边界出现（6:05～7:15）

旁白任务：把只读请求改成高风险写操作，解释凭据、审批、修订、限流和脱敏。

手绘画面节拍：

1. 原红色便签翻面：“取消 ORD-20250902-002”。
2. 凭据被放进 Server 侧保险箱，模型只拿到 `cred_*` 引用。
3. 请求经过风险闸门，被挂起为 awaiting approval。
4. 审批人把原因从“用户申请”改成“用户确认取消”，再盖批准章。
5. 审计打印机吐出 Trace，token 字段被黑条遮住。
6. 旁边的计数器和域名围栏表示限流、白名单。

关键字幕：

- “模型不能拿密钥”
- “高风险工具：先审批，再执行”
- “审计保存最终参数，不只保存模型提案”

源码证据：

- `src/lob_mcp/governance.py` 第 74～90、93～188 行。
- `src/lob_mcp/management.py` 第 185～264 行。

### 10｜超时和取消必须真的传到底层（7:15～7:55）

旁白任务：区别前端隐藏按钮与协作式取消。

手绘画面节拍：

1. `demo.wait` 沙漏开始转动。
2. 用户按下红色取消按钮。
3. 红色取消信号沿 Management API → Task → MCP Client → Server 反向传播。
4. Invocation 时间线从 running 变为 cancelled。
5. 最终收据展示 `started → cancelled`。

源码证据：

- `src/lob_mcp/client.py` 第 132～151 行。
- `src/lob_mcp/management.py` 第 167～216 行。

### 11｜管理台不是装饰，它把协议变成可运营系统（7:55～8:40）

旁白任务：展示 PostgreSQL 持久化、CapabilitySnapshot、Invocation、Approval 和 Event。

画面组合：手绘结构图与真实录屏混合。

手绘节拍：

1. Server 配置落入 PostgreSQL。
2. 初始化后，Tools/Resources/Prompts 形成能力快照。
3. 每次调用生成 Invocation，状态事件沿时间轴追加。

录屏节拍：

1. 在管理台注册 stdio Server。
2. 状态从 connecting 变成 ready。
3. 打开能力详情。
4. 调用 `order.query`。
5. 打开审计详情与 Event 时间线。
6. 打开审批中心完成 `order.cancel`。

源码证据：`README.md` 第 139～145 行，以及 `management.py` 第 94～264 行。

### 12｜FastMCP、Inspector 与项目边界（8:40～9:30）

旁白任务：说明这是手写协议研究实现，不是假装替代成熟框架；展示官方兼容证据。

手绘画面节拍：

1. 左边是 LOB MCP 的透明机械结构，能看见 JSON-RPC、Transport 和 Registry 齿轮。
2. 右边是 FastMCP 工具箱，标注 Provider、Middleware、OAuth、Tasks。
3. 官方 Inspector 像质检员，依次在 Tools、Resources、Prompts 上盖通过章。
4. 未实现能力放在虚线边界外：Sampling、Elicitation、OAuth、多副本 Event Store。

关键结论：自己实现一遍，是为了看懂协议；生产选型仍要尊重成熟框架和安全边界。

源码证据：

- `docs/FASTMCP_SOURCE_MAP.md`。
- `docs/COMPATIBILITY_REPORT.md`。
- `docs/PRODUCTION_RISKS.md`。

### 13｜结尾：MCP 真正标准化的是什么（9:30～10:00）

旁白任务：回收开场悬念，给出一句可记忆结论并引导 GitHub。

手绘画面节拍：

1. 开场那堵墙被替换成标准插座。
2. Agent 不再知道订单系统细节，只看到能力契约。
3. 最终完整链路缩回一张手绘总图。
4. 展示 `lobster-bujiaban/lob-mcp`、Apache 2.0、查看源码、使用、Star。

建议收尾句：

> Function Calling 让模型表达“我想调用什么”；MCP 让外部系统用统一方式回答“我能提供什么，以及怎样安全地调用我”。

## 五、节奏控制

- 开场 3 秒内必须出现失败结果和完整链路缩略图。
- 每段拆成四个连续步骤，约每 4～7 秒推进焦点；订单便签随步骤移动，保持视觉连续。
- 每个章节最多引入 3 个新概念。
- 技术名词首次出现时显示中英对照，后续只保留短中文。
- 代码证据每次只展示 4～8 行，先高亮入口，再沿箭头追到下一层。
- 录屏只承担“证明能运行”，原理解释全部由手绘图承担。
- 章节之间用订单便签移动完成转场，不用反复黑场标题。

## 六、字幕与排版

- 底部字幕每行不超过 18 个汉字，最多两行。
- 字幕只保留口语语义，不逐字堆叠英文方法名。
- 顶部长期保留小角标：`LOB MCP · 虾哥不加班公开研发`。
- 源码证据出现时，右上角显示文件与行号，停留至少 3 秒。
- 手机安全区：核心对象放在画面中间 70%，底部 260px 不放关键图形。
